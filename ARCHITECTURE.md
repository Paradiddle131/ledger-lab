# Architecture

The current design, and each major choice with its reason and what it rejected.
Rewritten in place: it describes the system as it is now.

## Components and seams

Real public documents are fetched, landed and loaded into the warehouse; an open-source ERP posts them into journal lines; layered models turn both into certified data products; governed metrics sit on top; one agent answers from them and another drafts entries a named human approves.
A control plane (identity, tool policy, approval, guardrails, audit, traces, evals, cost caps) spans every agent call.

| Component | Runs on | Seam | State |
|---|---|---|---|
| `ingest/`: download scripts with checksums, landing | the session, then Cloud Storage | a landing path from the environment | not built yet |
| Warehouse | DuckDB in the session until the lab project exists, then BigQuery | the dbt profile's target, chosen by `LEDGER_LAB_GCP_PROJECT` | local engine built; BigQuery not built yet |
| `models/`: layered dbt models, contracts, quality checks, reconciliations | DuckDB through dbt-duckdb, then BigQuery through dbt-bigquery | [`models/profiles.yml`](models/profiles.yml), read from the environment | dbt project and a smoke model built and tested on DuckDB; layered models not built yet |
| ERP: posting engine and write target | Odoo in containers | the ERP's own API | not built yet |
| Orchestrator | Airflow in containers | one DAG per pipeline calling the pieces above | not built yet |
| `access/`: personas, their grants, policies, visibility tests | BigQuery row, column and masking rules | [`access/personas.yaml`](access/personas.yaml) | persona set and mapping built as data; each persona an identity a test acts as on DuckDB (the `as_persona` fixture over [`access/identities.py`](access/identities.py)), checked against a stand-in warehouse of every product; the BigQuery impersonation named, not run; row, column and masking policies not built yet |
| `semantics/`: governed metrics, glossary, verified queries | the platform's catalog, or a stand-in | metric definitions in the tree; the glossary in [`semantics/glossary.yaml`](semantics/glossary.yaml) | glossary built as data; metrics and verified queries not built yet |
| `agent/`: the governed data agent | the native data agent, own agent beside it | one question-to-answer interface | not built yet |
| `workflow/`: proposals and human approval | containers | one proposal-to-approval interface | not built yet |
| `controls/`: the controls catalogue | the tree | [`controls/catalogue.yaml`](controls/catalogue.yaml) | catalogue built as data; no control implemented yet |
| `platform/`: GCP definitions, container stack, cost fences | GCP free tier and the session | configuration from the environment; the stack's entry point is `make stack-up [PROFILE=<service>]` / `make stack-down` over [`platform/stack/compose.yaml`](platform/stack/compose.yaml) | stack skeleton built (the shared database service, checked by `docker compose config`); the project seam ([`platform/gcp_project.py`](platform/gcp_project.py), `LEDGER_LAB_GCP_PROJECT` only) and `make cost-check` built, the live billing read untried; the fresh-clone check (`make fresh-clone`) built; the spend fences defined in [`platform/gcp/`](platform/gcp) and validated offline, not applied; other GCP definitions not built yet |

The catalogues are YAML validated by a JSON Schema beside each file, and `tests/` checks their cross-references: every grant names a known persona, entity and product, every control's owner and every glossary term's owner is a human persona, a glossary term's references name other terms, and a control is marked implemented only once its proving test exists.

## Choices

- **Real public data, not generated data:** real records carry the revisions, negative awards, missing identifiers and revised figures that generated data leaves out, and those are what the controls must survive; rejected: generated data (clean by construction, so it proves nothing about mess), a well-known marketplace dataset (its non-commercial licence would bind everything derived from it).
- **Three public entities as the row boundary: City of Chicago (USD), UK Department for Transport (GBP), Dutch central government (EUR):** Chicago brings the only public contract to voucher to payment chain, the UK a second file layout and an April to March year, the Netherlands budget against outturn; together they give three currencies and three fiscal calendars to translate and consolidate; rejected: one entity (no row boundary, no translation), a private company's ledger (none is public).
- **Reference data from its publishers:** ECB reference rates translate currency, the GLEIF register matches vendor names to legal entities, and annual filings from the securities regulator give an independent figure to tie out against; rejected: a public warehouse copy of the filings (stale for years).
- **An open-source ERP (Odoo) as posting engine and write target:** it posts the real documents into journal lines by real accounting rules, loaded as SAP-shaped ledger tables, and is the system the acting agent drafts into; rejected: hand-written posting rules (accounting the lab invents), a vendor ERP (licensed and not free).
- **DuckDB through dbt-duckdb as the local engine until BigQuery takes over:** it runs in process with nothing to start, its dialect is the closest that works to BigQuery's (`QUALIFY`, structs and lists, window functions), and the switch is the dbt profile's target, which `LEDGER_LAB_GCP_PROJECT` selects, with the BigQuery adapter in its own dependency group; DuckDB enforces no row, column or masking rules, so the local access harness enforces them itself and the BigQuery proof stays the real one; dialect gaps are cast away in the model SQL (DuckDB's date truncation returns a timestamp, BigQuery's a date); rejected: a BigQuery emulator (partial dialect coverage, fragile under dbt, and it emulates none of the row and column rules), PostgreSQL (real row security and roles, but the farthest dialect and the largest rewrite at the switch).
- **Native GCP services only where free, a stand-in behind the same seam otherwise:** BigQuery enforces row, column and masking rules itself, which is the point; the platform's catalog, lineage and native data agent are used only once they prove free; rejected: stand-ins for everything (they prove nothing about the real platform's enforcement), paid managed services (the lab spends $0.00).
- **Personas as service identities that tests impersonate, with a mapping table in place of a group directory:** a test acts as a persona and asserts what the warehouse returns, on BigQuery by impersonating `<persona>@<project>.iam.gserviceaccount.com`, and the persona to entity to data product table in `access/` plays the directory's role; rejected: a group directory (needs an organisation and an administrator the lab does not have), personal accounts (need real people and email addresses in a public repo).
- **A persona on DuckDB is a database built for it, opened read-only with files and extensions locked out:** DuckDB has no users or roles, so the identity is what the connection can reach: a copy of only the products a `read`, `aggregate` or `edit` grant names, and of an entity-scoped product (its entity id in an `entity` column) only the granted entities' rows, so asking for anything else finds no table; `draft` and `post` read nothing in the warehouse, since the proposal and approval workflow carries the entry; rejected: views or a filter over the shared warehouse (a connection that can open the warehouse reads past them), a persona label the test honours (nothing enforces it).
- **Orchestration in plain containers, not Kubernetes:** Airflow, the ERP and their shared database fit one cloud session, and a cluster would teach nothing this lab is for; rejected: a managed cluster (not free), a local cluster (spends the session's memory on plumbing).
- **The native data agent first, an own agent as the comparison:** the native agent runs on the asking person's credentials, so the warehouse's rules apply unchanged; an own agent over the same metrics measures right answers, confident wrong answers, cost and auditability against it; rejected: an own agent only (rebuilds what the platform owns), the native agent only (no yardstick).
- **One Compose file with a profile per service for the container stack:** the shared PostgreSQL 16 server is the only service without a profile and always starts, and the ERP, lineage backend, orchestrator and tracing tool each join under a profile named after the service, so a session runs only what its item needs from one entry point (`make stack-up PROFILE=<service>`), and a fresh clone reproduces it; the database password comes from the environment and the port binds to loopback; rejected: one Compose file per service with its own database (more files to start and a database server each, spending the session's memory), the session's preinstalled PostgreSQL (cloud-only, so a clone cannot reproduce it).
- **Catalogues as data checked by tests:** the persona mapping and the controls catalogue are read by the tests that will prove them, so a claim and its proof cannot drift apart; rejected: tables in prose (nothing checks them).
- **Spend fences as OpenTofu definitions the owner applies:** `platform/gcp/` declares a budget of one unit of the billing account's currency on the lab project, credits included, alerting at 1, 3 and 5 hundredths, a BigQuery query cap of 30 GiB a day (inside the free 1 TiB a month), and a kill switch where the budget's Pub/Sub topic starts a Workflows run through Eventarc that unlinks billing above the kill threshold (5 units by default, in the account's currency, which must be one worth about a dollar); the pinned OpenTofu validates them with no backend, and a test reads them offline for the cap, the thresholds, the free-tier regions and a resource allowlist; a session never plans or applies them; rejected: a Cloud Run function for the kill switch (its image counts against Artifact Registry's free storage), fences set by hand in the console (nothing checks them), a kill threshold at the first cent (unlinking billing can delete resources, so the cents only alert).
- **One module names the GCP project, from `LEDGER_LAB_GCP_PROJECT` only:** a session can carry another lab's `GCP_PROJECT` and credential, so every caller asks `platform/gcp_project.py`, which never reads the foreign variable and refuses by name when it is the only project in sight; `make cost-check` reports $0.00 by absence without calling any GCP tool while no lab project is set, and with one set sums the month's cost net of credits from the billing export through a capped `bq` query and fails above zero; rejected: reading `GCP_PROJECT` with an override (one missing variable spends another lab's money), a cost check that always queries (a GCP call before the lab has a project).
- **Secret scan with detect-secrets pinned in the lock:** a plain clone runs it after `uv sync`; rejected: a scanner binary installed outside the project (absent in a plain clone).
- **A fresh clone checked for secrets, identifiers and data, in `make check`:** `platform/fresh_clone.py` clones the committed `HEAD` and fails on a tracked file `.gitignore` excludes, an email address off the reserved example domains, a GCP project id written as a value (setting, flag, `projects/` path, service-account domain) other than the documented placeholders, key material, or a secret-scan finding; a licence-confirmed sample added with `git add -f` will need an explicit exception there; rejected: scanning the working tree (it sees uncommitted files a clone never gets, and misses nothing a clone has), flagging every project-id-shaped word (ordinary hyphenated words have the same shape).
- **The roadmap and decisions on the tracker:** epics with sub-issues hold the plan and progress, a decision is weighed on its issue, and only its outcome lands here; rejected: plan and decision files (appended to, they go stale and pull the tree into its own history).
