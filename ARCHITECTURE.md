# Architecture

The current design, and each major choice with its reason and what it rejected.
Rewritten in place: it describes the system as it is now.

## Components and seams

Real public documents are fetched, landed and loaded into the warehouse; an open-source ERP posts them into journal lines; layered models turn both into certified data products; governed metrics sit on top; one agent answers from them and another drafts entries a named human approves.
A control plane (identity, tool policy, approval, guardrails, audit, traces, evals, cost caps) spans every agent call.

| Component | Runs on | Seam | State |
|---|---|---|---|
| `ingest/`: download scripts with checksums, landing | the session, then Cloud Storage | a landing path from the environment (`LEDGER_LAB_LANDING`, default `landing/`); sources recorded in [`ingest/sources.yaml`](ingest/sources.yaml) | fetch-and-verify kit built and tested against a local server (`python -m ingest.fetch <source>`); retrying a download whose connection drops; five sources recorded and landed: Chicago's contracts and payments (`ingest/chicago/`), through one shared step that hashes every vendor or payee who may be a person with the pseudonymiser ([`ingest/individuals.py`](ingest/individuals.py)), the ECB's daily euro reference rates for the pound and the US dollar (`ingest/ecb/`), the Dutch central government's budget statements for every year the publisher serves, one row per budget moment (`ingest/nl_government/`), and the GLEIF register's records for the vendors' countries, without what may name a person (`ingest/gleif/`, whose step uses the pseudonymiser's classifier to leave such records out and hashes nothing); the ECB and Dutch steps name no one; the kit refuses a source that names people until it has such a step; the Cloud Storage landing bucket declared in [`platform/gcp/`](platform/gcp) and validated offline, not applied |
| Warehouse | DuckDB in the session until the lab project exists, then BigQuery | the dbt profile's target, chosen by `LEDGER_LAB_GCP_PROJECT` | local engine built; BigQuery not built yet |
| `models/`: layered dbt models, contracts, quality checks, reconciliations | DuckDB through dbt-duckdb, then BigQuery through dbt-bigquery | [`models/profiles.yml`](models/profiles.yml), read from the environment | dbt project, a smoke model and the fiscal calendars (periods with their status, days) built and tested on DuckDB; layered models not built yet |
| ERP: posting engine and write target | Odoo in containers | the ERP's own API | not built yet |
| Orchestrator | Airflow in containers | one DAG per pipeline calling the pieces above | not built yet |
| `access/`: personas, their grants, policies, visibility tests | BigQuery row, column and masking rules | [`access/personas.yaml`](access/personas.yaml) | persona set and mapping built as data; each persona an identity a test acts as on DuckDB (the `as_persona` fixture over [`access/identities.py`](access/identities.py)), checked against a stand-in warehouse of every product, with aggregate grants reaching no rows until the minimum-group rule exists; one service account per persona, with the agent's token grants on each, declared in [`platform/gcp/`](platform/gcp) and validated offline, not applied; the BigQuery impersonation named, not run; row, column and masking policies not built yet |
| `semantics/`: governed metrics, glossary, verified queries | the platform's catalog, or a stand-in | metric definitions in the tree; the glossary in [`semantics/glossary.yaml`](semantics/glossary.yaml) | glossary built as data; metrics and verified queries not built yet |
| `agent/`: the governed data agent | the native data agent, own agent beside it | one question-to-answer interface | not built yet |
| `workflow/`: proposals and human approval | containers | one proposal-to-approval interface | not built yet |
| `controls/`: the controls catalogue | the tree | [`controls/catalogue.yaml`](controls/catalogue.yaml) | catalogue built as data; two controls implemented: individuals hashed before landing, and the lab spend fences checked live |
| `platform/`: GCP definitions, container stack, cost fences | GCP free tier and the session | configuration from the environment; the stack's entry point is `make stack-up [PROFILE=<service>]` / `make stack-down` over [`platform/stack/compose.yaml`](platform/stack/compose.yaml) | shared database built (one PostgreSQL server with a database per planned service, checked by `docker compose config` and live by `make stack-test`), the services under their profiles not built yet; the project seam ([`platform/gcp_project.py`](platform/gcp_project.py), `LEDGER_LAB_GCP_PROJECT` only) and `make cost-check` built, reading the billing export and every fence live; the fresh-clone check (`make fresh-clone`) built; the spend fences defined in [`platform/gcp/`](platform/gcp), validated offline, applied by the owner and read live by `make cost-check` (the budget is beyond the session account's reach, so the check reports it as not checked); the persona identities, their token grants and the landing bucket declared beside them and validated offline, not applied; other GCP definitions not built yet |

The catalogues are YAML validated by a JSON Schema beside each file, and `tests/` checks their cross-references: every grant names a known persona, entity and product, every control's owner and every glossary term's owner is a human persona, a glossary term's references name other terms, and a control is marked implemented only once its proving test exists.

## Choices

- **Real public data, not generated data:** real records carry the revisions, negative awards, missing identifiers and revised figures that generated data leaves out, and those are what the controls must survive; rejected: generated data (clean by construction, so it proves nothing about mess), a well-known marketplace dataset (its non-commercial licence would bind everything derived from it).
- **Three public entities as the row boundary: City of Chicago (USD), UK Department for Transport (GBP), Dutch central government (EUR):** Chicago brings the only public contract to voucher to payment chain, the UK a second file layout and an April to March year, the Netherlands budget against outturn; together they give three currencies and three fiscal calendars to translate and consolidate; rejected: one entity (no row boundary, no translation), a private company's ledger (none is public).
- **Reference data from its publishers:** ECB reference rates translate currency, the GLEIF register matches vendor names to legal entities, and annual filings from the securities regulator give an independent figure to tie out against; rejected: a public warehouse copy of the filings (stale for years).
- **An open-source ERP (Odoo) as posting engine and write target:** it posts the real documents into journal lines by real accounting rules, loaded as SAP-shaped ledger tables, and is the system the acting agent drafts into; rejected: hand-written posting rules (accounting the lab invents), a vendor ERP (licensed and not free).
- **DuckDB through dbt-duckdb as the local engine until BigQuery takes over:** it runs in process with nothing to start, its dialect is the closest that works to BigQuery's (`QUALIFY`, structs and lists, window functions), and the switch is the dbt profile's target, which `LEDGER_LAB_GCP_PROJECT` selects, with the BigQuery adapter in its own dependency group; DuckDB enforces no row, column or masking rules, so the local access harness enforces them itself and the BigQuery proof stays the real one; dialect gaps are cast away in the model SQL (DuckDB's date truncation returns a timestamp, BigQuery's a date); rejected: a BigQuery emulator (partial dialect coverage, fragile under dbt, and it emulates none of the row and column rules), PostgreSQL (real row security and roles, but the farthest dialect and the largest rewrite at the switch).
- **Fiscal calendars as a period table and a day table built from a seed of each entity's first month, over the fiscal years one dbt var (`fiscal_years`) names, with period status as a seed of one row per period:** each year is twelve calendar months from the entity's first month (January for Chicago and the Dutch government, April for the UK department), labelled by the calendar year it opens in (the UK's 2024-25 is 2024) and numbered from period 1, so a day falls in one period and later models join on entity, year and period; dbt data tests hold the rules (one period per day, contiguous periods, the UK year opening on 1 April and closing on 31 March, a status for every period); a date outside the covered years has no row, so a later model tests each date column with the project's `dates_in_fiscal_calendar` test, which fails where a join would silently drop the row; and dbt-core's own cross-database date spine and date macros keep the SQL unchanged for BigQuery; the Dutch budget moments are versions of one year's budget, not periods a day falls in, so the calendar leaves them out and a budget-against-outturn model will carry its moment beside the year; rejected: labelling a year by the year it closes in (the UK writes 2024-25, opening year first), dbt-utils for the date spine (a package download for what dbt-core ships), a case per entity in the SQL (a new entity would be a code change, not a row).
- **Native GCP services only where free, a stand-in behind the same seam otherwise:** BigQuery enforces row, column and masking rules itself, which is the point; the platform's catalog, lineage and native data agent are used only once they prove free; rejected: stand-ins for everything (they prove nothing about the real platform's enforcement), paid managed services (the lab spends $0.00).
- **Personas as service identities that tests impersonate, with a mapping table in place of a group directory:** each persona id is a service account id, `platform/gcp/` declares one account per persona read from `access/personas.yaml` itself, with no project role, and the agent account may mint tokens on each of them and nowhere else; a test acts as a persona and asserts what the warehouse returns, on BigQuery by impersonating `<persona>@<project>.iam.gserviceaccount.com`, and the persona to entity to data product table in `access/` plays the directory's role; rejected: a group directory (needs an organisation and an administrator the lab does not have), personal accounts (need real people and email addresses in a public repo).
- **A persona on DuckDB is a database file named after it, opened read-only with no other file reachable, no extension beyond DuckDB's built-in ones, and its configuration locked:** DuckDB has no users or roles, so the identity is the catalog the connection opens, which it cannot rename or leave, and what that catalog holds: a copy of only the products a `read` or `edit` grant names, and of an entity-scoped product (its entity id in an `entity` column) only the granted entities' rows, so asking for anything else finds no table; an `aggregate` grant reaches no rows until the minimum-group rule exists, and `draft` and `post` read nothing in the warehouse, since the proposal and approval workflow carries the entry; DuckDB lets every connection create temporary objects that shadow unqualified names, so a persona's reach is read through qualified names (`system.main.current_database()`, `"<persona>".main.<product>`), and a shadow can forge only what its own connection shows under an unqualified name, never reach another product; rejected: views or a filter over the shared warehouse (a connection that can open the warehouse reads past them), a persona label the test honours (a temporary macro overrides it).
- **Orchestration in plain containers, not Kubernetes:** Airflow, the ERP and their shared database fit one cloud session, and a cluster would teach nothing this lab is for; rejected: a managed cluster (not free), a local cluster (spends the session's memory on plumbing).
- **The native data agent first, an own agent as the comparison:** the native agent runs on the asking person's credentials, so the warehouse's rules apply unchanged; an own agent over the same metrics measures right answers, confident wrong answers, cost and auditability against it; rejected: an own agent only (rebuilds what the platform owns), the native agent only (no yardstick).
- **One Compose file with a profile per service for the container stack:** the shared PostgreSQL 16 server is the only service without a profile and always starts, and the ERP, lineage backend, orchestrator and tracing tool each join under a profile named after the service, so a session runs only what its item needs from one entry point (`make stack-up PROFILE=<service>`), and a fresh clone reproduces it; the image's init-script folder creates one database per planned service (ERP, lineage backend, orchestrator, agent session store, workflow checkpointer) on first start, from one list in the Compose file that the live test also reads, and the healthcheck asks over TCP because the first-start server answers only on its socket until those scripts finish; the password comes from `LEDGER_LAB_DB_PASSWORD`, else from a file `make stack-up` generates and git ignores; each checkout is its own Compose project on a free loopback port, so checkouts sharing a Docker daemon never meet; `make stack-down` removes the volume and the generated password with the containers, because init scripts run only on an empty volume and the stack holds nothing a script cannot rebuild; rejected: one Compose file per service with its own database (more files to start and a database server each, spending the session's memory), the session's preinstalled PostgreSQL (cloud-only, so a clone cannot reproduce it), a volume kept across `make stack-down` (a changed database list or password would silently not apply), a fixed host port and project name (sibling checkouts on one daemon would fight over them).
- **A vendor or payee is an organisation only on evidence, and every other name becomes a keyed HMAC-SHA-256 (`ingest/individuals.py`, key `LEDGER_LAB_HASH_KEY`):** the evidence is a name the caller knows is an organisation, or a legal form of a separate legal person (final UK, Dutch or US forms, leading Dutch foundation, association or cooperative forms) whose remaining words are one plain party, with no joiner of a second party (a comma except one directly before the form, a dash, slash, bracket, dot or `&`, a word such as `and`, `as` or `c/o`, a title, a person's suffix, a role such as executor or guardian, a trust) and, before `B.V.` or `N.V.`, which also read as a surname's initials, two words that are neither single letters nor name particles, while a trading-as or also-known-as part, an estate, executors or a deceased overrides even the register; the failure that matters is a person in clear, so sole traders and partnerships, which are no separate legal person, are hashed, and so are real companies with a joined name (`Doe & Roe Ltd`, `Acme (UK) Ltd`, `Rolls-Example Ltd`, `Dr Example Drinks Ltd`) until the register knows them, while a company named after a person with nothing joined (`Jane Doe Ltd`) passes in clear on purpose, being a legal person of its own; a person becomes `person:` and the 64-digit hex HMAC of the name after NFKC, straight quotes, invisible format characters dropped, case folding, whitespace collapsed and edge punctuation stripped, a missing payee stays missing, and the pseudonymiser refuses to start without a key of at least 32 characters (the classifier alone needs none); rejected: a person-name detector (it must know every name of every culture, and its misses are leaks), an unkeyed hash (a list of candidate names reverses it), a default or file-held key (anyone with the tree could reverse the hashes).
- **One fetch kit verifies every source in memory before writing, with a per-source step between:** `ingest/fetch.py` streams the bytes the publisher serves into memory, undecoded (it asks for no content encoding, so the hash is the one a published checksum gives), compares their SHA-256 with the one recorded in `ingest/sources.yaml`, and only then hands them to the source's own step (`STEPS`, by source name) or, with none, writes them as they are, through a temporary file and a rename that leaves nothing behind on failure; an entry must say whether it names people, and one that does is refused before any request until it has a step, so unverified bytes never reach the landing path and a source that names people never has its raw bytes on disk; a failing step is reported by source and kind only, since its message could quote names; the cost is a source bounded by memory, so a response over 512 MiB or still arriving after 30 minutes fails; rejected: streaming to a temporary file and hashing as it lands (raw bytes, names included, would touch disk), a script per source (each would re-implement the verification).
- **A source that names people lands as text Parquet, built in memory, with every possibly-personal payee hashed together with whatever links to them, across all rows:** Chicago's contracts and payments land through one shared step (`ingest/chicago/table.py`, configured in `contracts.py` and `payments.py`); a vendor id seen beside any hashed name hashes every name it carries and is itself replaced by a keyed `id:` hash, which still joins but cannot be looked up; a hashed vendor's rows lose their description, street address, ZIP code and contract PDF link, and a description or address on any row whose run of words is a hashed name is blanked too, since descriptions repeat names in truncated and reordered forms and other vendors' rows mention them; payments have no id, address or description, and their step refuses a voucher or contract number that is not a code (a digit and no space, or the placeholders `DV` and `Multiple`); contract, specification and voucher numbers stay in clear as the keys between the tables, though the City's public search can look a hashed payee up by them, and a company named after a person stays in clear where that person is hashed elsewhere; the rows never touch disk (an in-memory filesystem between the CSV and DuckDB's Parquet writer); every column stays the publisher's text and typing is the models' job; a landed test (`pytest -m landed`, left out of `make check`) profiles each file and hashes every run of words of every clear cell against its hashed names; rejected: replacing the name inside the description (leaves reordered and truncated forms), blanking only the hashed row's own cells (other rows name the person), a temporary file for the scrubbed rows (a killed step leaves it behind), typing columns at landing (a bad value would fail the land instead of being counted).
- **Chicago's payments are one pinned query, every row the portal created by the cut-off (`:created_at`), not slices by year:** the whole table is about 476,000 rows and 38 MB as served, a fourteenth of the kit's 512 MiB cap, so one checksum covers it and any one fiscal year is a filter on the landed file; the cut-off is the portal's row-creation time because payments with check dates years old arrive every day, so a check-date cut-off would move daily, and the City reloads the whole table when it rolls payments up, which moves the hash and fails the fetch loudly until it is re-pinned; rejected: one source per year (two dozen checksums for a table that fits one, and the rolled-up and itemised rows of a year would need two filters), raising the byte cap (nothing needs it).
- **A download whose connection drops is run again from the first byte, three attempts in all with a wait of 5 and then 10 seconds, inside the one 30-minute deadline:** Chicago's portal closes some long responses before their end and a rerun completes byte for byte, so a closed connection, a body cut short or a timeout (`httpx.NetworkError`, `RemoteProtocolError`, `TimeoutException`) is retried by a loop in `ingest/fetch.py`, while an error status, a proxy refusal, the byte cap, the deadline and a checksum mismatch fail at once, since each is an answer, not a lost one (a portal's passing 503 is rerun by hand); rejected: httpx's transport `retries` (it retries only connecting, never a body cut short), resuming with a `Range` request (portals' pinned queries need not honour it, and the bytes would come from two responses), a retry library (one more dependency for a ten-line loop).
- **The GLEIF register pinned as one dated golden-copy file, landed for the vendors' legal-address countries (GB, NL, US) without what may name a person:** the publisher writes a dated file once and keeps serving it (files from the register's first years still answer, last modified within days of publishing), so a re-fetch next month verifies, and it publishes no country slices, so the whole-world CSV archive (about 507 MB, 5 GB unzipped) is the smallest fixed file; it fits the kit's 512 MiB cap with about 30 MB to spare, which the newest file's growth of about 4 MB a month uses up in about half a year, so a later re-pin needs the download streamed through the step, not a raised cap; the step (`ingest/gleif/legal_entities.py`) refuses an archive declaring more than 6 GiB unzipped, decompresses and reads the CSV one record at a time in memory, so the unfiltered file never touches disk, writes only the screened records to a private work folder under the landing path, and keeps the names, legal form, country, jurisdiction, category, statuses and last-update date as served text; doubt means a person, so a record never lands when the register files it as a sole proprietor (its LEI finds the name again, so hashing would hide nothing), when its category is blank or unknown, when its legal-form code is a sole proprietorship or a partnership that is no separate legal person (the Dutch firm, maatschap, limited partnership and rederij, the US general partnerships), or when it has no real legal-form code (blank, other, not available) and the pseudonymiser's classifier does not call its legal name an organisation; an other or transliterated name the classifier does not call an organisation is blanked; each drop is counted by reason in the file's metadata; not screened are the legal names of records with a real legal-form code, partnerships that only a free-text legal form reveals (an English general partnership has no code) and other names the classifier passes, and matching on a headquarters address is out of scope; so the matching lets a register entry vouch that a name is an organisation only when its legal-form code makes a separate legal person, never a record without one; rejected: pinned API queries by country (each day's updates and the paging change the bytes), the daily and monthly delta files (changes, not a state), hashing a sole proprietor's name (its LEI reverses it), matching free-text legal forms for sole traders (open-ended, and a miss is a person in clear), dropping the whole register entry of a company with a person-like other name (it loses the company for one doubtful name).
- **The Dutch central government lands from its budget statements (Rijksbegrotingsstaten), one row per article, kind of amount, year and budget moment, for every year the file serves:** the one fixed file carries every article's draft, supplementary and outturn amounts side by side for every year since 2013, so budget against outturn needs no join across files; the step turns the moment columns into rows named by the publisher's own column names, keeps every column as the publisher's text, a blank as empty text, with each amount in thousands of euros and the unit on every row, refuses a year that is not four digits, and keeps each served row's position as an integer, since the publisher serves some articles on two rows that each carry part of their moments; every year lands, since the file is small and the models filter to the years the fiscal calendars cover; rejected: the budget tables per moment (Budgettaire Tabellen: a file per moment with its own amount columns, outturn only from 2024, and free-text detail names that could name a recipient), the file in its served wide shape (no moment on the row), rescaling to euros at landing (typing is the models' job), landing only the covered years (a second copy of the calendar's years, and a quiet drop of an oddly written year).
- **A live table is pinned as an ordered query with a cut-off, both required by the schema:** an entry's `query` names the portal's own order and cut-off parameters, joined to the fixed ones (a row limit) its URL already carries, so a re-fetch asks for the same rows in the same order and a revised row behind the cut-off shows as a checksum drift that fails loudly; the order is every column of content, since rows that tie on all of them are identical bytes; rejected: a fixed export URL (the live table grows under it), storing a copy of the rows (data in the tree), the portal's row id as the order (the City recreates rows under new ids, so the same rows could come back in another order).
- **The ECB reference rates are pinned as one data-API query (`EXR`, daily rates of the pound and the US dollar against the euro) from the first covered year to a fixed end date, as data-only CSV recorded as a plain `url`, and land as text Parquet of one row per date and currency:** a query bounded by a past end date serves the same bytes on every request, and of the API's formats only the CSV carries no time the response was prepared; it has no order parameter and serves each series in date order, so the entry is a fixed URL, not an ordered query; a day the settlement system is closed has no row, so a gap is an absent date, never a zero; rejected: the history file (it grows every working day, so its checksum drifts daily), the XML or JSON formats (each carries the time the response was prepared), the CSV with attributes (series titles and notes could change the bytes without a rate changing), a float column (it would change the published figure).
- **httpx as the HTTP client, sending one fixed name, `ledger-lab research-bot`, to every host:** it follows redirects, honours the session proxy and its CA bundle from the environment, and is typed for pyright; rejected: the standard library's `urllib` (hand-written redirect and error handling), requests (untyped without stubs).
- **Catalogues as data checked by tests:** the persona mapping and the controls catalogue are read by the tests that will prove them, so a claim and its proof cannot drift apart; rejected: tables in prose (nothing checks them).
- **Spend fences as OpenTofu definitions the owner applies:** `platform/gcp/` declares a budget of one unit of the billing account's currency on the lab project, credits included, alerting at 1, 3 and 5 hundredths, a BigQuery query cap of 30 GiB a day (inside the free 1 TiB a month), and a kill switch where the budget's Pub/Sub topic starts a Workflows run through Eventarc that unlinks billing above the kill threshold (5 units by default, in the account's currency, which must be one worth about a dollar); the pinned OpenTofu validates them with no backend, and a test reads them offline for the cap, the thresholds, the free-tier regions, a resource allowlist and that no project-level role reaches anyone but the kill switch; a session never plans or applies them; rejected: a Cloud Run function for the kill switch (its image counts against Artifact Registry's free storage), fences set by hand in the console (nothing checks them), a kill threshold at the first cent (unlinking billing can delete resources, so the cents only alert).
- **The hand-made agent account referenced by its id, and the landing bucket beside the fences:** `platform/gcp/` looks the agent account up from `agent_account_id` and grants it token creation on the persona accounts and object rights (`roles/storage.objectUser`) on one bucket only, named from the project id, Standard class in the fences' free-tier region, with uniform access, public access prevented and soft delete off, so only live objects count against Cloud Storage's always-free 5 GB-months and an empty bucket costs nothing; rejected: declaring the agent account (the owner would first import it, and a destroy would delete the session's own credential), an object role on the project (it would reach every bucket the project ever holds).
- **One module names the GCP project, from `LEDGER_LAB_GCP_PROJECT` only, and `make cost-check` reads the cost and the fences live:** a session can carry another lab's `GCP_PROJECT` and credential, so every caller asks `platform/gcp_project.py`, which never reads the foreign variable and refuses by name when it is the only project in sight; `make cost-check` reports $0.00 by absence without calling any GCP tool while no lab project is set; with one set it dry-runs, then runs under a byte cap fixed in code, one `bq` query for the month's cost net of credits, the month's rows and the newest export time, and fails unless that is one row with a cost of $0.00 from an export that holds rows for the project, since an empty export proves nothing; it reads the billing link, the query cap, the kill switch's workflow, trigger, subscription, topic, account and project roles, and the budget over their REST APIs with `curl`, and compares each with its declaration, which `platform/fences.py` reads from `platform/gcp` for this check and the offline tests alike; it asks `testIamPermissions`, never an attempt, whether the agent could move a fence, on the project, the billing account and the kill switch's account; it fails on a missing, differing, unreadable or malformed fence and on any such permission, and reports a budget or project policy this account may not read as not checked, naming the API's reason, neither passing nor failing; its output names fences by role and prints no identifier or API message; rejected: reading `GCP_PROJECT` with an override (one missing variable spends another lab's money), a cost check that always queries (a GCP call before the lab has a project), a Google client library (one more dependency where `bq` and `curl` through the session's proxy already read everything), expected values copied into the check (they drift from what is applied), a byte cap from the environment (a setting that could only loosen it).
- **Secret scan with detect-secrets pinned in the lock:** a plain clone runs it after `uv sync`; rejected: a scanner binary installed outside the project (absent in a plain clone).
- **A fresh clone checked for secrets, identifiers and data, in `make check`:** `platform/fresh_clone.py` clones the committed `HEAD` and fails on a tracked file with a data extension (those `.gitignore` names as data, in any letter case) other than the dbt seeds it lists by name, whatever the ignore rules say, a tracked file `.gitignore` excludes, a `.gitignore` exception other than one naming a listed seed, an email address off the reserved example domains, a GCP project id written as a value (setting, flag, `projects/` path, service-account domain) other than the documented placeholders, key material, or a secret-scan finding; each seed is named in both the check and `.gitignore`, so a new one, or a licence-confirmed sample, is a reviewed change to both; rejected: scanning the working tree (it sees uncommitted files a clone never gets, and misses nothing a clone has), flagging every project-id-shaped word (ordinary hyphenated words have the same shape).
- **The roadmap and decisions on the tracker:** epics with sub-issues hold the plan and progress, a decision is weighed on its issue, and only its outcome lands here; rejected: plan and decision files (appended to, they go stale and pull the tree into its own history).
