# Architecture

The current design, and each major choice with its reason and what it rejected.
Rewritten in place: it describes the system as it is now.

## Components and seams

Real public documents are fetched, landed and loaded into the warehouse; an open-source ERP posts them into journal lines; layered models turn both into certified data products; governed metrics sit on top; one agent answers from them and another drafts entries a named human approves.
A control plane (identity, tool policy, approval, guardrails, audit, traces, evals, cost caps) spans every agent call.

## Choices

- **Real public data, not generated data:** real records carry the revisions, negative awards, missing identifiers and revised figures that generated data leaves out, and those are what the controls must survive; rejected: generated data (clean by construction, so it proves nothing about mess), a well-known marketplace dataset (its non-commercial licence would bind everything derived from it).
- **Three public entities as the row boundary: City of Chicago (USD), UK Department for Transport (GBP), Dutch central government (EUR):** Chicago brings the only public contract to voucher to payment chain, the UK a second file layout and an April to March year, the Netherlands budget against outturn; together they give three currencies and three fiscal calendars to translate and consolidate; rejected: one entity (no row boundary, no translation), a private company's ledger (none is public).
- **Reference data from its publishers:** ECB reference rates translate currency, the GLEIF register matches vendor names to legal entities, and annual filings from the securities regulator give an independent figure to tie out against; rejected: a public warehouse copy of the filings (stale for years).
- **An open-source ERP (Odoo) as posting engine and write target:** it posts the real documents into journal lines by real accounting rules, loaded as SAP-shaped ledger tables, and is the system the acting agent drafts into; rejected: hand-written posting rules (accounting the lab invents), a vendor ERP (licensed and not free).
- **DuckDB through dbt-duckdb as the local engine until BigQuery takes over:** it runs in process with nothing to start, its dialect is the closest that works to BigQuery's (`QUALIFY`, structs and lists, window functions), and the switch is the dbt profile's target, which `LEDGER_LAB_GCP_PROJECT` selects in a session with no `GCP_PROJECT`, with the BigQuery adapter in its own dependency group; DuckDB enforces no row, column or masking rules, so the local access harness enforces them itself and the BigQuery proof stays the real one; dialect gaps are cast away in the model SQL (DuckDB's date truncation returns a timestamp, BigQuery's a date); rejected: a BigQuery emulator (partial dialect coverage, fragile under dbt, and it emulates none of the row and column rules), PostgreSQL (real row security and roles, but the farthest dialect and the largest rewrite at the switch). The BigQuery dialect gaps met at the switch are fixed in the shared SQL or by a dispatch macro: identifiers quoted with `adapter.quote`, decimal literals typed exact with `exact_decimal` (BigQuery types `0.05` as FLOAT64), a `having` over a select alias named through its table, and the seeds' integer type per engine; the BigQuery target sends the environment's gcloud access token (`oauth-secrets`) when `CLOUDSDK_AUTH_ACCESS_TOKEN` is set, else Application Default Credentials.
- **The local DuckDB database is `models/target/ledger_lab.duckdb` under the folder dbt runs from, unless `LEDGER_LAB_DUCKDB_PATH` names another file:** it sits in the project's target folder, which dbt-core 1.12 makes when it parses the project, before the adapter opens the database, so a build from the repository's root in a fresh clone needs no folder made first; `dbt clean` empties that target folder (`clean-targets` in `models/dbt_project.yml`), so it removes the default local database with it; `make contract-test` reads the build there and writes the Data Contract CLI's copy to `target/ledger_lab.cli.duckdb`, the file the contract's `local` server names, making that folder first; rejected: a tracked root `target/` (an ignore exception the fresh-clone check refuses), moving dbt's target path to the root (it would move the semantic manifest `mf` reads).
- **Fiscal calendars as a period table and a day table built from a seed of each entity's first month, over the fiscal years one dbt var (`fiscal_years`) names, with period status as a seed of one row per period:** each year is twelve calendar months from the entity's first month (January for Chicago and the Dutch government, April for the UK department), labelled by the calendar year it opens in (the UK's 2024-25 is 2024) and numbered from period 1, so a day falls in one period and later models join on entity, year and period; dbt data tests hold the rules (one period per day, contiguous periods, the UK year opening on 1 April and closing on 31 March, a status for every period); a date outside the covered years has no row, so a later model tests each date column with the project's `dates_in_fiscal_calendar` test, which fails where a join would silently drop the row; and dbt-core's own cross-database date spine and date macros keep the SQL unchanged for BigQuery; the Dutch budget moments are versions of one year's budget, not periods a day falls in, so the calendar leaves them out and the budget-against-outturn model carries each moment as a column beside the year; rejected: labelling a year by the year it closes in (the UK writes 2024-25, opening year first), dbt-utils for the date spine (a package download for what dbt-core ships), a case per entity in the SQL (a new entity would be a code change, not a row).
- **Currency is translated by the `translate_currency` macro through the ECB's euro rates, one rate set a day in `fx_rates`: the set of the posting or payment date, the previous business day's when that day is closed (carried at most four days), the cross rate through the euro, or with `constant_rates_on` one named day's set for every row (constant currency); results round once, half away from zero, to two decimal places, and an amount no rate translates stops the query:** the ECB publishes each currency against the euro only, so dollars to pounds is the amount divided by dollars per euro and multiplied by pounds per euro, rounded once so it never drifts a penny from its two legs; `fx_rates` spreads each publication date over the days before the next, so its days follow the published rates whatever years the calendars cover; four days is the longest run of closed days in the published rates (Good Friday to Easter Monday, or 25 and 26 December beside a weekend), so a longer gap, a day before the first rate or after the last, and an unknown or missing currency have no rate, and the macro raises an error naming the currencies and the day (both engines spell it `error(message)` and evaluate it only on the row a `case` sends to it), since a null would vanish from a sum and a caller could forget its test; a null amount stays null; rates are decimals of six places and amounts dbt's `type_numeric` (`numeric(28,6)` on DuckDB), and because DuckDB divides decimals as floats, which misround a half cent (542.05 dollars on 5 April 2024 are exactly 428.865 pounds), the DuckDB quotient is taken exactly in 128-bit integers, while BigQuery divides in BIGNUMERIC, rounding to cents from 38 decimal places; the `source_rows` var, one for every fetched source through the `landed_or_sample` macro, reads the landed file by default, so a run with nothing landed fails on the missing file, and the builds in the tests pass `sample` to read committed windows of real rates (25 March to 8 April 2024: a weekend, and Good Friday to Easter Monday; and for the group totals 29 December 2023 and the whole of March 2026; the ECB allows free use with the source cited); rejected: rounding the euro leg first (a cent's drift from the cross), carrying a rate with no limit (a missing week would reuse a stale rate silently), a null for a missing rate with a not_null test each caller adds (a forgotten test lets a sum skip the row), dividing BigQuery's NUMERIC (rounded to 9 places, then to cents, it can round twice near a half cent for amounts with more than 2 decimal places), a day spine from the fiscal calendars (rates outside their years would silently get no row), a package for the fill (a window and a five-row offset in dbt-core do it), the sample as the default (a real run would quietly translate with test fixtures), rates built at test time from a download (`make check` would need the network).
- **The Dutch budget against outturn is one row per budget line, year and kind of amount (`budget_against_outturn`), the figures as the publisher's file serves them: each budget moment a column in euros, the latest moment the file serves for the year as its current budget, named in `current_budget_moment`, the outturn in its own column beside it, and `has_doubtful_zero` on a line the file may serve a zero in place of a figure, over a staging model that types the landed rows (`stg_nl_government__budget_moments`):** served rows of one year, kind, chapter code and article number are one line only on the file's evidence, a non-zero figure repeated across them and none that differs, the line taking each moment's figure once, and otherwise each row is its own line, numbered within the code (`line_in_article`); of the real file's 152 pairs sharing a code, 48 are one article on two rows that repeat the later moments, and the rest stay apart: 40 are chapter `IIB` carrying a chapter `III` (Algemene Zaken) article, 48 are chapter `IX` holding national debt and taxes under one number until 2020, 10 are chapter `L` holding the Nationaal Groeifonds beside Foreign Affairs or Klimaatfonds articles, 4 are chapter `A`, whose name alternates between Mobiliteitsfonds and Infrastructuurfonds, and 2 are the 2024 unallocated reserve, whose rows repeat nothing; the chapter name is left out of the match because chapter `A` is served under both names in one year, and tests fail on a figure repeated across two lines, on a line of two rows with no repeat, on a new pair that neither repeats nor differs, on a served figure no line carries, and on a line that differs from a figure the publisher's annual reports print; a moment with no non-zero amount anywhere in a year is not served in the file for that year (2026's first and second supplementary budgets and outturn, and the September one before 2023), so it is null on every line; a zero at a served moment is the figure as served, which is sometimes a figure the file leaves out (the 2023 second supplementary budget for chapter XII prints 290,715 and 109,767 thousand for articles 16 and 13, where the file serves 0), so a zero between non-zero figures of a line, or a zero draft before non-zero figures at every later moment, sets `has_doubtful_zero`; wrong figures pass through as served and the landed tests count each kind (a 2025 first supplementary figure about three times too high, one over a hundred times its neighbours, an article served under two chapter codes), never correcting them; the current budget is the second supplementary, September supplementary, first supplementary or draft figure, the first the file serves for the year, and the outturn never fills it; amounts are dbt's `type_numeric` in euros, the published thousands times 1,000, never a float; the years are those the fiscal calendar covers for the entity, by a join to `fiscal_periods`; names are trimmed and the two doubly encoded letters the file serves are repaired with `replace`, and a test fails on any new one;
